# SubMate 갱신 결정 플랜

작성일: 2026-10-30 · 대상: 창업자 1인 · 목표: 만들고 반응 보기 (수익화 없음)

## a. 한 줄 정의

**결제 3일 전에, 끊어도 손해 없는지 알려주는 앱.**

지금과 달라지는 점은 세 가지다. 홈 첫 화면의 주인공이 "이번 달 구독료 총액"에서 "이번 주에 결정할 결제"로 바뀐다. 해지 안내의 중심이 "어디서 어떻게 끊나"에서 "지금 끊으면 언제까지 쓸 수 있나"로 바뀐다. 알림은 결제 예고가 아니라 결정 요청이 되고, 누르면 바로 결정 화면으로 간다.

## b. 문제와 가설

문제는 **갱신 순간**에 있다. 사용자는 결제가 나간 뒤에야 아깝다고 느끼고, 그때는 이미 늦다. 미리 알려주는 앱은 많지만 "그래서 지금 끊으면 손해인가"에는 답하지 않는다. 이 플랜은 그 한 질문에 답하는 데 제품을 맞춘다.

| 가설 | 검증 방법 | 측정 지표 | 성공 기준 |
| --- | --- | --- | --- |
| H1 활성화: 3분 안에 2개를 등록하면 다음 주기가 온다 | 지인 5명 첫 세션 관찰 | 첫 세션 시간, 등록 개수 | 70% 이상이 3분 내 2개 등록 |
| H2 알림을 열면 24시간 안에 결정한다 | D-3 알림을 연 뒤 24시간 행동 추적. 실제 도달 여부는 테스터에게 직접 물어 확인한다(로컬 알림은 도달을 보고하지 않음) | 알림 열람→24시간 내 결정 | 연 사람 중 30% 이상 |
| H3 해지 시점 정보를 믿는다 | 뱃지 노출 후 이용 행동, 인터뷰 | 결정 화면 체류, "언제까지 쓸 수 있나" 오해 건수 | 실제 해지 완료 1건 이상, 오해 0건 |
| H4 절약 기록이 재방문을 만든다 | 2주 후 무작위 연락 | 주 2 재방문 | 5명 중 2명 이상 자발적 재방문 |

가설은 지인 5명 규모에서 방향만 본다. 5명 결과로 통계적 확신을 말하지 않는다.

## c. 핵심 루프 6단계

| 단계 | 사용자 행동 | 화면 | 목표 |
| --- | --- | --- | --- |
| 1 | 결제 3일 전 알림을 받는다 | 알림 | 0탭 |
| 2 | 알림을 눌러 결정 화면을 연다 | Renewal Hub | 1탭, 3초 |
| 3 | 지금 끊으면 언제까지 쓰는지 확인한다 | Renewal Hub | 5초, 0탭(읽기) |
| 4 | 유지 또는 해지를 고른다 | Renewal Hub | 1탭, 5초 |
| 5 | 해지 화면을 열고, 끝나면 기록한다 | 해지 가이드 | 2탭, 60초 |
| 6 | 아낀 금액이 자동으로 쌓인다 | 홈 | 0탭 |

첫 세션 목표는 **2개 구독을 3분 이내**에 넣는 것이다. 현재 온보딩은 구독당 4탭(카테고리→서비스→설정 모달→시작)이라 2개면 8탭이다. 목표는 구독당 2탭(서비스 선택, 저장)이며 나머지는 기본값으로 채운다.

## d. 화면과 카피

**1) 빠른 등록** — 목적: 첫 세션에서 결제일만 받고 나간다. 배치: 서비스 그리드(자주 쓰는 12개) → 금액·결제일 두 칸만 노출(기본값 채움) → 저장. 주 동작 "저장", 보조 동작 "나중에 추가". 빈 상태(목록 없음): 직접 추가 한 줄만 둔다. 오류: "저장하지 못했어요. 금액과 결제일만 다시 확인해 주세요."

- "결제일만 알려주세요. 나머지는 나중에 고쳐도 돼요."
- "다음 결제일"
- "2개만 넣어도 충분해요. 첫 알림은 3일 전에 보내드려요."
- "나중에 추가할게요"

**2) 홈 "이번 주 결정"** — 목적: 이번 주에 정할 것만 보여준다. 배치: 최상단 카드에 결정 대기 건수와 금액, 그 아래 3일 내 결제 목록, 총액은 접힌 보조 영역으로 내린다. 주 동작 "결정하기", 보조 동작 "이번 주는 넘기기". 빈 상태: "이번 주에 정할 결제가 없어요." 오류: "결제일을 불러오지 못했어요. 구독 목록에서 확인해 주세요."

- "이번 주 결정 2건"
- "3일 뒤 결제 · 17,000원"
- "끊어도 11월 14일까지 쓸 수 있어요" (기간 유지 서비스에만. 즉시 종료 서비스는 "끊으면 바로 끝나요")
- "이번 주는 넘길게요"

**3) 갱신 결정 화면(Renewal Hub)** — 목적: 한 화면에서 근거와 결정을 끝낸다. 배치: 상단에 결제일·금액, 가운데 해지 시점 카드(뱃지+출처+확인일), 하단에 유지·끊기 두 버튼. 두 버튼은 같은 크기와 같은 색으로 나란히 두고 **기본 선택은 없다**. 사용 여부를 묻는 한 탭은 선택 사항으로, 건너뛰어도 결정에 영향이 없다. 빈 상태: "정할 결제가 없어요. 다음 결제일이 오면 알려드릴게요." 오류: "해지 시점 정보를 불러오지 못했어요. 서비스 공식 안내를 확인해 주세요."

- "3일 뒤 17,000원이 결제돼요"
- "지금 끊으면 11월 14일까지 쓸 수 있어요"
- "해지 시점은 확인이 필요해요"
- "서비스 공식 안내 열기"
- "유지할게요" / "끊을게요"

**4) 해지 가이드와 완료 기록** — 목적: 해지 실행을 돕고 결과를 남긴다. 배치: 결제 경로별 3단계 체크리스트, 공식 화면 열기 버튼, 완료 후 "해지했어요" 확인. 주 동작 "해지 화면 열기", 보조 동작 "아직 안 했어요". 빈 상태: "해지 안내를 준비 중이에요. 공식 고객센터에서 확인해 주세요." 오류: "해지 화면을 열지 못했어요. 브라우저에서 직접 열어 주세요."

- "Google Play에서 해지해야 해요"
- "해지 화면 열기"
- "해지했어요" / "아직 안 했어요"
- "이번 달 아낀 금액 17,000원"

정책을 모르는 서비스에는 시점을 추정하는 문장을 쓰지 않는다. 위 "확인 필요" 카피만 쓴다.

## e. 해지 시점 신뢰 규칙 (가장 중요)

이 제품의 유일한 자산은 "시점이 맞다"는 신뢰다. 틀린 시점 한 번이면 나머지 정확도는 의미가 없다. 규칙은 다음 다섯 가지다.

1. **뱃지는 조건을 모두 만족할 때만** 붙인다: `source_url` 있음, `checked_at` 180일 이내, 그 출처가 해당 경로를 직접 설명. 하나라도 없으면 뱃지 없이 "확인 필요"로 표시한다.
2. **기본값은 unknown**이다. 정책 데이터가 없거나 만료됐으면 unknown이지, "아마 기간 만료"가 아니다.
3. **경로별 정책**을 지원한다. 멜론은 "정기결제해지"면 만료일까지 유지, "중도해지"면 즉시 종료·환불이다. 버튼 이름이 다르면 결론도 다르므로 하나의 값으로 합치지 않는다.
4. **스토어 결제가 서비스 정책을 이긴다.** Google Play·App Store 결제는 항상 기간 만료 시 해지이며 서비스 웹사이트에서 끊을 수 없다. 이 경우 서비스 정책 문구를 보여주지 않는다.
5. **위약금은 금액이 아니라 경고로** 보여준다. Adobe 연간 플랜은 남은 기간 요금의 50%를 물릴 수 있다. 추정 금액은 "예상"으로 표기하고 확인 필요를 함께 적는다.

현재 데이터에서 고칠 것: 네이버플러스와 쿠팡플레이는 제목("즉시 종료·환불")과 요약("회차 마지막 날까지 유지")이 서로 반대다. 제목을 지우고 요약 하나만 남기거나, 실제 버튼 경로가 둘이면 경로별로 나눈다. 근거를 다시 확인하기 전까지 이 두 서비스와 디즈니+, 배민클럽, ChatGPT Plus는 **확인 필요**로만 노출한다.

| 필드 | 값 | 쓰임 |
| --- | --- | --- |
| `cancel_effect` | period_end / immediate_prorated / immediate_loss / contract_penalty | 결정 화면의 결론 한 줄 |
| `confidence` | verified / moderate / unknown | 뱃지 노출 여부 |
| `source_url` | 서비스 공식 안내 URL | "공식 안내" 링크, 뱃지 근거 |
| `checked_at` | YYYY-MM-DD | 180일 지나면 자동 unknown |
| `scope` | service / path / rail | 경로 충돌 처리 단위 |

바꿀 파일: `src/data/cancelPolicies.js`(필드 추가, 모순 항목 정리), `src/lib/cancelTiming.js`(뱃지 조건·스토어 우선·경로 분기), `src/components/CancelModal.jsx`(출처·확인일 표시, unknown 문구), 테스트 `tests/cancelPolicies.test.js`·`tests/cancelTiming.test.js`(모순·만료 회귀 방지).

## f. 알림 규칙

- **D-3만 결정을 요청한다.** D-1은 D-3 알림 이후 결정이 없을 때만 보낸다.
- 서비스 하나당 주기 하나에 알림 하나. 같은 주기에 D-3·D-1·당일이 겹쳐도 최대 2회다. **사용 여부를 묻는 별도 알림("잘 쓰셨어요 / 거의 안 썼어요")은 없앤다.** 한 서비스가 주기에 세 번 알림을 만들던 구조를 끊고, 사용 여부 질문은 Renewal Hub 안의 선택형 한 탭으로 옮긴다.
- **월간 요약은 해지 기록이 1건 이상인 사용자에게만** 보낸다. 아직 아낀 것이 없는 사람에게 요약을 보내면 알림만 늘어난다.
- 조용한 시간 21:00~08:00에는 보내지 않고 08:00으로 미룬다. 이때 **라벨은 고정 D-3이 아니라 실제 발송 시점의 남은 일수로 다시 계산한다.** 21:00에 D-3이던 알림은 다음 날 08:00에 D-2로 나간다.
- 알림 권한은 앱 시작 때가 아니라 **첫 구독을 저장한 직후**에 요청하고, 이유를 함께 적는다: "3일 전에 알려드릴게요". 거부하면 홈에 "이번 주 결정" 배지를 띄워 같은 정보를 앱 안에서 보여준다.
- 누르면 Renewal Hub로 바로 간다. 현재 결제 알림은 상세·에이전트 응답으로 열리는데, 이 경로를 Renewal Hub로 통일한다.

| 상황 | 제목 | 본문 |
| --- | --- | --- |
| 기간까지 유지 | [결제 D-3] 넷플릭스 17,000원 | 끊어도 11월 14일까지 볼 수 있어요. 지금 정할까요? |
| 즉시 종료 | [결제 D-3] 멜론 10,900원 | 지금 끊으면 남은 3일은 못 봐요. 3일 뒤 10,900원이 결제돼요. |
| 확인 필요 | [결제 D-3] 쿠팡플레이 7,890원 | 해지 시점은 확인이 필요해요. 공식 안내를 함께 보여드릴게요. |
| 스토어 결제 | [결제 D-3] 유튜브 프리미엄 14,900원 | Google Play에서 해지해요. 기간이 끝날 때까지 볼 수 있어요. |

## g. 계측

지금은 분석 도구도 이벤트 테이블도 없다. 지인 5명 단계에서는 숫자 6개면 충분하다. `product_events` 테이블을 추가한다: `user_id`, `name`, `props`(jsonb), `created_at`. RLS는 본인 행만 insert·select 가능하게 하고, 집계는 창업자가 service role로 조회한다. 로컬 알림은 도달을 보고하지 않으므로 **도달률은 이벤트가 아니라 테스터에게 직접 물어 확인한다.**

| 이벤트 | 언제 | props 핵심 |
| --- | --- | --- |
| onboarding_completed | 온보딩 종료 | added_count, duration_sec |
| subscription_added | 구독 저장 | service_id, channel, source(onboarding/home) |
| renewal_viewed | Renewal Hub 열림 | subscription_id, entry(alert/home) |
| decision_made | 유지/해지 선택 | decision, confidence, alert_kind, hours_since_alert |
| cancel_completed | 해지 완료 기록 | channel, method(steps/proof) |
| savings_recorded | 절약 금액 확정 | amount_krw, month |

창업자가 볼 쿼리 4개.

```sql
-- 1. 활성화: 온보딩을 3분 안에 끝내고 그때 2개 이상 등록한 사람 비율
select count(*) filter (where (props->>'duration_sec')::int <= 180
                          and (props->>'added_count')::int >= 2) * 100.0
       / nullif(count(*), 0) as pct
from product_events
where name = 'onboarding_completed'
  and created_at > now() - interval '14 days';

-- 1b. 참고용: 온보딩 후 24시간 안에 2개 이상 등록 (활성화와 다른 지표)
with onboarded as (
  select user_id, min(created_at) done_at
  from product_events where name = 'onboarding_completed' group by 1
), added as (
  select e.user_id, count(*) n
  from product_events e join onboarded b using (user_id)
  where e.name = 'subscription_added' and e.created_at <= b.done_at + interval '24 hours'
  group by 1
)
select count(*) filter (where coalesce(n, 0) >= 2) * 100.0 / nullif(count(*), 0) as pct
from onboarded left join added using (user_id);

-- 2. 알림을 열고 24시간 안에 결정한 비율
with viewed as (
  select props->>'subscription_id' sub, min(created_at) first_view
  from product_events
  where name = 'renewal_viewed' and props->>'entry' = 'alert'
  group by 1
), decided as (
  select props->>'subscription_id' sub, min(created_at) first_decision
  from product_events where name = 'decision_made' group by 1
)
select count(*) filter (where first_decision <= first_view + interval '24 hours')
       * 100.0 / nullif(count(*), 0) as pct
from viewed left join decided using (sub);

-- 3. 알림 종류별 결정 건수
select props->>'alert_kind' kind, count(distinct props->>'subscription_id') decided
from product_events where name = 'decision_made' group by 1 order by 2 desc;

-- 4. 해지 완료와 절약 기록, 2주 재방문
select user_id, bool_or(name = 'cancel_completed') cancelled,
       bool_or(name = 'savings_recorded') saved, count(*) events
from product_events where created_at > now() - interval '14 days' group by 1;
```

### 이번 주에 바로 할 일

빌드보다 먼저 테스터를 모은다. 지인 5명을 이번 주에 확보하고, 그중 **14일 안에 갱신일이 오는 사람을 최소 2명** 넣는다. 각 테스터의 결제 경로(카드 직접결제·Google Play·App Store)를 표에 적어 둔다. 이 준비가 없으면 알림이 갈 시점 자체가 없어서, 제품 문제가 아니라 일정 문제로 지표가 비게 된다.

## i. 2주 지인 테스트

모집: 지인 5명, 조건은 구독 4개 이상·서로 다른 결제 경로 2개 이상(카드 직접결제, Google Play 또는 App Store)·14일 안에 갱신 있는 사람 2명 이상.

스크립트(유도 금지): "요즘 정기결제로 나가는 거 뭐 있어요?" → 앱을 건네며 "써 보고 어떤지 알려줘." → 관찰만 하고 기능 설명은 묻기 전에는 하지 않는다. 마지막에 "결제 전에 이걸 왜 볼 것 같아요?" 한 번만 묻는다.

| 지표 | 정의 | 기준 |

| 활성화 | 첫 세션 3분 내 2개 등록 | 70% 이상 |

## k. 하지 않을 것

- 마이데이터 연동: 심사와 계약이 필요하고, 지금은 반응을 보는 단계다.
- 자동 해지 대행: 남의 계정에서 해지를 확정하는 일은 동의·책임 범위를 넘는다.
- 결제 승인 에이전트: 결제 권한을 쥐는 순간 규제와 사고 책임이 제품보다 커진다.
- B2B·제휴 영업: 사용자 반응이 없는데 영업부터 하면 검증이 아니라 영업이 된다.
- 프로모션 우선: 혜택 목록은 결정을 돕지 않고 화면만 늘린다.
- AI 채팅을 메인 진입으로: 결정은 대화보다 한 화면의 비교가 빠르다.
- 공유 구독 정산: 돈이 오가는 기능은 첫 검증 대상이 아니다.
- 수익화 설계: 창업자 목표는 만들고 반응을 보는 것이다.
